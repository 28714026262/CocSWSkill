# 通用P6：规则、数据与执行配置

本页把已采用的故事、人物、信息与场景行动变为可执行处理。它不预定骰制、主持人、属性表或战斗系统。首期具体系统适配只有[COC](systems/coc/README.md)；其他现成系统须取得其实际规则及版本后另作配置，不能宣称已获支持。项目可以明确采用自订约定，按本页写清权限、条件与后果；自订可用不等于兼容某官方系统。

## 1. 先恢复采用规则和处理权限

读取本轮范围及同版P2因果、P3实体、P4事件／信息和P5实际场景。局部只读受影响对象。登记系统、版本、可选项、自订项、角色来源、固定与可改范围及本次实际产物。区分官方条款、项目对条款的应用、设计建议和改变规则的特例；每项指向可核来源或明确的自订采用记录，未核条款注明影响。

明确谁提出行动、确认事实、判断前提、选择代价、记录状态和处理争议。主持制可由主持裁定；无主持可用公开条件表、当事人选择、轮值核对和约定的争议处理。若分歧时的处理会决定成败，先写默认办法，例如先执行双方认可的无争议部分，争议部分保留原状态并共同查采用条款；不能默认暗中由作者或某玩家决定。秘密信息可由各自材料提供，不因无主持就强制全部公开。

完成依据：当前对象实际使用哪套处理、由谁执行、哪些规则已核均可回答。一般非互动剧本只整理正文及制作标注，不新增玩家卡、骰值或执行手册。

## 2. 从实际行动提取角色与对象需求

逐个追踪目标→角色想做的动作→接触／权限／知识／工具／人手前提→可能改变的对象→结果用途。例如“救人”需分定位、接近、解除障碍、稳定搬护及撤离，不能一个总成功替代所有动作；作品不需要细分的普通动作可以合并处理。

区分角色知道什么、玩家作出何种推断、角色能执行什么。先判断行动有无不确定性、风险或稀缺取舍：条件明确且无有意义风险可直接兑现，前提欠缺可说明缺项并保留其他选项；只有采用规则需要时才作随机检定。重要线索、作者预定后期材料、战斗或推理的存在都不自动要求检定。推理与战斗各按作品侧重保留真实设计责任，不强造谜题、遭遇或数值。

涉及可玩角色一致性时读取[角色配置](character-configuration.md)及其唯一两步总方法，不从职业名直接推定能力。对抗和协作还要提取另一方的能力、知情、位置与资源，避免只给主角填数。

完成依据：每项配置都服务具体动作或状态；必要行动、失败后的行动和团队缺席影响均有处理对象。

## 3. 为对象选字段、单位和依据

按当前机制定义最少字段，不套一张全系统表。每项说明含义、类型／单位、默认或初始状态、取值依据、适用条件、派生关系及版本。区分初始参数与游玩后的当前值；例如“剩余时段”是离散整数，不能与分钟未经换算混加。资源注明归属、消耗时机、是否共享、恢复和上限；派生值可从采用规则重算。

人物、物件、敌人、伤势、环境和其他对象只填实际会使用的项，沿用项目ID。规则不给某个数值时，选择有依据的项目设计并明示，或保留待核；不能写成“通用标准”。物件布景不是自动可领取资源，数字正确也不能创造不存在的工具。决定性参数未核时，可交候选与影响，相关可运行承诺保持未完成。

## 4. 写默认处理及条件变化

将每种动作写成实际可查的处理单元，可合入原场景而不新建一套真相：

| 项目 | 必须能确定的内容 |
|---|---|
| 输入与前提 | 当前状态、对象、意图、方法、位置、权限、信息、工具和人手 |
| 默认处理 | 直接成立／条件不满足／有代价的选择／采用规则下的检定或对抗；谁确认及依据 |
| 条件变化 | 新证据、工具、协作、关系、环境、准备和时间怎样改变前提或处理，不以玩家口才替代角色方法 |
| 结果 | 得到的具体信息、实际成果、未改变部分与状态更新；取得、理解、相信、证明和执行分别成立 |
| 代价与反馈 | 消耗在何时发生，参与者何时看见什么，迟到／失败／中断分别失去与保留什么 |
| 重复与并行 | 相同条件重做是否有新结果，换方法需哪些前件；谁可同时做什么，共享资源和世界时钟怎样结算 |

先给默认方案再给可调条件，不能只列“由现场决定”。无骰也可因前提不满足、资源耗尽、拒绝代价或错过窗口而未达成；不能把“无骰”写成一切成功。失败不强制保送信息，也不能用唯一一次失手堵死作品承诺的必要推进：核实已有的替代取得、不同执行方法、代价路线及其共同关口，必要时返修结构。无来源的新证据或万能NPC不算冗余。

提前取得材料就兑现其可读部分；已有充分认识可以提前改变方案。没发生的事件不会先产生材料，已存在的材料也不因章节没到而失效。知情只按实际接触和传播更新。已经取消的前件停止未来事件，既成损坏、消耗和成果各按机制保留。

## 5. 完成机制并反查前序

存在持续状态、异常、协作、追踪、资源循环或规则特例时，按[机制方法](mechanisms.md)完成触发、反馈、抵抗、取消和结束。机制中需要的具体系统值在相应适配核验，不能以“特殊”掩盖无来源。

反向检查配置是否支持已承诺的行动、事件、证明、路线与节奏。合法角色不具备必要能力、搬护超出通道、费用使所有方案都失效时，辨明缺的是人物权限、世界实体、信息、操作、规则或数值，再按[依赖循环](../../scenario-writing/references/common/workflow.md)返修对应处。允许在授权内修改设计；已有角色卡、固定历史和玩家未来决定各保原权限。改后同步原对象、状态、场景、地图和时间影响，再回当前动作复核。

## 6. 提取执行参考并验证

从已完成设计提取执行表或规则提示：对象／版本、适用状态、动作前提、默认处理、条件调整、具体结果、成本反馈、重复取消、来源和待核。主持制可形成主持参考；无主持形成参与者可直接使用的公开流程与必要私密卡，不加KP职位。表链接同版正文，不能在手册里临时补决定性设计。

按实际涉及内容走查正常、不介入、有效干预、未达成但留有变化、关键失败、低能力／缺角色、提前成果、重复、分队及取消；局部不凑齐无关用例。每例追踪输入→处理→后果及保留状态。纸面可执行、工具已实现、实际运行和真人体验分别记录；只做文字配置不授工具或游玩资格。

## 7. 虚构无骰救援完整例

以下是独立虚构设计，参数全为本例自订约定，不是工程、医疗或官方规则。作品采用三名参与者、无骰无主持合作。每人决定自己角色行动；行动者指出前提，一名未行动者按公开表核对，状态共同登记。对前提有分歧时只结算双方同意的部分，争议动作暂停、保留原状态，查本例条款后共同决定；暂停不扣游戏时段。没有隐藏主持裁定。

**采用输入。** P2规定伤员林在泵房，洪水源持续启动；P3固定宽廊与高架道两条连接：宽廊可运板，清障后可通，高架道仅能单人轻装通行。P4的现场铭牌清楚标出断泵拉杆位置，无需推理解锁。P5已约定三名角色都能在机房和泵房间行动；角色甲懂停泵步骤，乙可照护并有夹具，丙有撬杆。未来如何分工由参与者决定。单位是本例离散“时段”，不代表真实分钟。

**初始字段。** 水势剩余窗口=4时段；泵=启动；宽廊=堵塞；伤员=待夹固、不可自行行走；夹具=1件可复用；运板=1块；撬杆=1根。每人每时段承担一个任务；只允许不同人在不同操作点并行。全员声明本段动作后同时结算，窗口减1；若停泵在本段结算成立，本段后不再减窗口。抵达角色当前所在区的普通行走已计入下表任务耗时，不能用此约定推及任意距离。相同工具不能被两项同时占用。

| 动作与输入 | 处理和时耗 | 具体后果与反馈 |
|---|---|---|
| 停泵：任一人已读铭牌、可到拉杆且未被占用 | 花1时段，直接关停 | 泵=停止，水声下降；取消此后窗口递减，已经积水保留；不自动清障或治伤 |
| 清障：宽廊堵塞、有撬杆、1人 | 花2个连续时段；每段可在段末选择中断 | 完成则宽廊=可运板；中断时只保留已搬开的碎物，重新开工还需剩余段数；持续敲击声是反馈 |
| 夹固：伤员待夹固、乙或已听乙说明者、夹具 | 花1时段，无检定 | 伤员=已夹固但仍不可自行行走，夹具随伤员占用；伤员明确示意可准备转移 |
| 运出：伤员已夹固、宽廊可运板、运板、2人 | 共同花1时段 | 伤员=已到安全平台；两人各占任务，板在平台。途中若不满足门路不启动此动作 |
| 独自走高架道：轻装1人 | 花1时段 | 该人可撤到平台；留下人员与伤员状态不变，不算完成救援 |

窗口减至0而泵仍启动时，泵房转为不可进入；正在泵房的人按本例已公开的撤出窄梯到机房，放下无法携带的运板，伤员留在原处。本例救援目标失败，已经撤出的人、停用的其他设施和记录均保留。此后可收束撤离，不能无限重复“进泵房运人”。参与者事前可见水位刻线和各段递减，不在最后一刻追加规则。

**可执行路径。** 第1段甲停泵，乙夹固，丙清障第一段；同时结算后泵停、伤员夹固、宽廊还未通，水窗口保留为4。第2段丙完成清障，其余人可等待或选择其他已定义动作。第3段任意两人按前提运出，第三人自行撤出。若玩家先读铭牌后由丙停泵也成立；甲并无排他职业门禁。停泵只是取消未来恶化，不抹除当前积水，宽廊和搬护仍需处理。

**缺项及拒绝。** 没有撬杆时，已约定两人可不用工具清障、共同占3连续时段；这是宽廊同一障碍的替代执行方法，共享泵房窗口，不能称独立逃生路线。缺乙时已取得的夹固说明可让别人执行；若夹具缺失，本例没有已采用替代，先返修或明示不能完成救援，不能临场生成设备。选择不救可按高架道离开，伤员后果按窗口发展；角色不被强制牺牲。

**反例自查。** “先各掷一次定位、照护、搬运”违反采用无骰约定且无必要不确定性；“高架道也是出口所以能抬伤员”违反几何；“三人各清一次障算三条备份”共用同一障碍；“停泵后伤员自动恢复”越过夹固与搬护；“缺夹具就给旧卡加医疗值”既改卡又不补实体。正确处理均回到具体前提、状态和既有权限。以上只是作者纸面例，不代表真人运行通过。
